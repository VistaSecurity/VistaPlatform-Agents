# Sensor configuration and log locations

Where the Vista Platform sensor keeps its configuration, certificate, logs and
state, on each system.

## Installed sensor

The installers write a YAML configuration file and start the sensor with
`-config <file>`. The file holds the registration key until the sensor redeems
it, so it is readable by the service account only (mode 0600 on Linux and
macOS; Administrators and SYSTEM on Windows).

| | Linux | macOS | Windows |
|---|---|---|---|
| Program | `/opt/vista-sensor/vista-sensor` | `/usr/local/vista-sensor/vista-sensor` | `%ProgramFiles%\VistaSensor\crypto-sensor.exe` |
| Configuration | `/opt/vista-sensor/sensor-config.yaml` | `/usr/local/vista-sensor/etc/sensor-config.yaml` | `%ProgramFiles%\VistaSensor\sensor-config.yaml` |
| Data path (`storage.dataPath`) | `/opt/vista-sensor/data` | `/usr/local/vista-sensor/data` | `%ProgramFiles%\VistaSensor\data` |
| Log | the systemd journal: `journalctl -u vista-sensor` | `/Library/Logs/Vista/sensor/sensor.log` | `<data path>\logs\sensor.log` |

On Windows the sensor writes its own log to `<dataPath>\logs\sensor.log`,
which moves to `sensor.log.1` at 10 MB (one backup is kept). On Linux and
macOS it logs to standard error, which systemd and the launchd job collect.

## The configuration file

What the installers write (Linux example):

```yaml
# Vista Platform Sensor configuration (generated by install-sensor.sh)
# sensorId holds the sensor's name until it registers, then its UUID.
sensorId: "sensor-host01-20261111"
controlPlaneUrl: "https://vista.example.com"
registrationKey: "REG-..."
reportingIntervalSeconds: 30

capture:
  interfaces: ["eth0"]
  activeProbing: true
  networkDiscovery: true

storage:
  dataPath: "/opt/vista-sensor/data"
```

When the sensor registers, it rewrites the file: `sensorId` becomes the UUID the
platform accepted, a `security:` section records the paths of its certificate,
private key and the platform CA, and, once the platform has issued the sensor
its own secret, the key is replaced by its SHA-256 (`registrationKeySha256`).
Settings the console manages, such as the additional TLS ports, are written
back into the file when the platform delivers them.

Every key the sensor reads is in
[`examples/sensor/config.example.yaml`](../../examples/sensor/config.example.yaml).
Keys are flat camelCase; a key the sensor does not know is ignored.

**Choosing interfaces on Windows:** an entry in `capture.interfaces` can name an
adapter by its name as Windows shows it and as the sensor reports it
(`Ethernet 2`, `Wi-Fi`), by its description
(`Intel(R) Ethernet Connection I219-V`), or by its Npcap device name
(`\Device\NPF_{GUID}`). With `interfaces: []` (what `install-sensor.ps1` writes
when `-Interfaces` is not given) the sensor captures on every adapter that is up
and has an address; loopback, tunnel and WAN Miniport devices are never picked.
If none qualifies, or a named interface matches no capture device, the sensor
stops **before** it registers, so the registration key is not used, and says
which names it accepts.

### Precedence

1. Command-line flags (for example `-verbose`, `-test`, `-ca-fingerprint`).
2. Environment variables the sensor reads, which override the file where set:
   for example `CONTROL_PLANE_URL`, `DATA_PATH`, `INTERFACES`,
   `REPORTING_INTERVAL`, `DEDUP_TTL_MINUTES`, `OWNED_NETWORKS`,
   `THIRD_PARTY_TLS_ENRICHMENT`, `VERBOSE`. An enrolled sensor keeps the
   `controlPlaneUrl` it enrolled with and ignores `CONTROL_PLANE_URL` unless
   `CONTROL_PLANE_URL_OVERRIDE=1` is also set. The Linux and macOS services set
   `SENSOR_IP_ADDRESS` to the installer's `--ip`.
3. The configuration file.
4. Built-in defaults.

Settings the platform delivers (for example `dedupTTLMinutes`, the probing
consent, the additional TLS ports) win over the local values once delivered.

## The data path

```text
<dataPath>/
├── certs/                       # written after registration (directory 0700)
│   ├── client.crt               # the sensor's certificate
│   ├── client.key               # its private key (0600), generated on this host
│   └── ca.crt                   # the platform CA
├── logs/sensor.log              # Windows: the sensor's log
├── platform-probe-consent.json  # the platform's probing settings as last delivered
└── test-discoveries.log         # test mode only
```

The private key is generated on the host and never leaves it. See
[CERTIFICATE_MANAGEMENT.md](CERTIFICATE_MANAGEMENT.md).

## A sensor run by hand

A sensor started without `-config` and with no data path set uses an OS default:

| System | Default data path |
|---|---|
| Linux | `/var/lib/vista-sensor` (`/var/lib/crypto-sensor` if only that exists) |
| macOS | `~/Library/Application Support/CryptoSensor` |
| Windows | `%LOCALAPPDATA%\CryptoSensor` |

`DATA_PATH` in the environment, or `storage.dataPath` in a file given with
`-config`, overrides it. Running the binary by hand is for troubleshooting and
evaluation only: see [USAGE_GUIDE.md](USAGE_GUIDE.md).

## Test mode log

With `-test`, discoveries and heartbeats go to `<dataPath>/test-discoveries.log`
instead of the platform, one JSON object per line:

```json
{"timestamp":"2026-11-11T10:15:30Z","type":"discovery","message":"Cryptographic implementation discovered","data":{"protocol":"TLS","dest_ip":"192.0.2.1","port":443}}
```

The file moves to `test-discoveries.log.<unix time>` at 10 MB, and the five most
recent backups are kept.

```sh
# Count discoveries by protocol
jq -r 'select(.type == "discovery") | .data.protocol' test-discoveries.log | sort | uniq -c
```
